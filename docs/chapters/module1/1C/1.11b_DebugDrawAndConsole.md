# Chapter 1.11b — Debug Draw 3D and Panku Console 🧰

**You cannot learn physics you cannot see — and your first GDScript addon called from C#**

🪜 **Scaffolding: 75 / 25.**

---

## 🎯 Goal

By the end you will **see** the collision shapes, velocities and contacts that [1.11](1.11_TheFourBodyTypes.md) could only describe, you will have **measured what each addon costs your APK**, and you will have called a **GDScript addon from C#** — which does not work the way you expect.

---

## 🏃 Fast-Track Summary

*Path C: install Debug Draw 3D, do Steps 2–4 and ⭐ P1, skip Panku.*

- **First: Godot has this built in.** `Debug → Visible Collision Shapes` costs nothing and solves half the problem. **Try the free thing before adopting the dependency** ([0.15](../../module0/0C/0.15_EvaluatingADependency.md)).
- 🧰 **Debug Draw 3D** — draw lines, spheres, boxes and text in the 3D world, from code, in the running game. **It is a GDExtension**, so it ships **native binaries** and **has a real C# API**.
- 🧰 **Panku Console** — an in-game console for running expressions live. **It is a pure GDScript addon**, so from C# you call it **by string**, with no compile-time checking.
- 🚨 **That difference is the chapter.** GDExtension → real C# types. GDScript addon → `Call("method_name", args)` and hope.
- 💰 **Measure the cost.** Debug Draw 3D ships an `.so` per Android ABI. Export before and after and record the delta ([0.12](../../module0/0B/0.12_MeasuredTwoLanguages.md)).
- Strip debug-only addons from release builds. A drawing library in a shipped APK is dead weight.
- Commit: `ch 1.11b: physics made visible`

## 🔨 Build

### Step 1 — Use the free thing first

Before installing anything: run `Main.tscn` and turn on **Debug → Visible Collision Shapes** `[UNVERIFIED]`.

Every collider draws as a wireframe. Now go back to [1.11](1.11_TheFourBodyTypes.md)'s Diagnose #2 — the cube resting half a metre above the floor on an oversized shape — and look at it with this on.

**One second.** No dependency, no build, no APK cost.

> 🚨 **This step exists to make adoption honest.** [0.15](../../module0/0C/0.15_EvaluatingADependency.md)'s last question is *"could I write this in a day?"*, and there is one before it: **"is it already there?"** A surprising amount of what people install is a nicer wrapper around something the engine ships. Write down what the built-in view does **not** give you — that list is your actual requirement:
>
> - ❌ arbitrary shapes at arbitrary places (a predicted landing spot, a raycast that hit nothing)
> - ❌ vectors — you cannot draw a velocity
> - ❌ text in the world
> - ❌ anything **on the phone**, where the editor's debug menu is not available

That fourth one is the decisive one for this course.

### Step 2 — Evaluate, then install

Run [0.15](../../module0/0C/0.15_EvaluatingADependency.md)'s checklist on **Debug Draw 3D** *(`DmitriySalnikov/godot_debug_draw_3d`)* and record the result in [`DecisionsLog.md`](../../../meta/DecisionsLog.md) as a dated 🔍 entry ([T-023](../../../meta/ToDos.md)):

| Question | Record |
|---|---|
| Licence | `[UNVERIFIED]` — read `LICENSE` in the repo. Expect MIT. |
| Last commit | |
| C# viability | **Ships a generated C# API** — check for `native_api/cs/` |
| Mobile cost | **Native `.so` per ABI.** Measure it in Step 5. |
| Abandonment risk | GDExtension — an engine bump can break a binary you cannot rebuild |
| Could I write it? | Lines and spheres, yes. Batched, on-device, with text — no. |

> ⚠️ **The abandonment row is not boilerplate for a GDExtension.** A GDScript addon that stops being maintained still *runs*; you can read and patch it. A native extension is compiled against a specific Godot ABI, and when Godot 4.x+1 changes it, **you need the author to rebuild** or you need a C++ toolchain and the will to use it. That is a genuinely higher risk, and it is the right price for a debug-only tool and the wrong one for something in your shipping path.

Install via the **AssetLib** tab, or by copying the release into `addons/` `[UNVERIFIED]`. Then:

1. **Project → Project Settings → Plugins → enable it** `[UNVERIFIED]`.
2. **Restart Godot.** GDExtensions load at startup.
3. Pin the exact version in [`ENGINE_VERSION.md`](../../../../ENGINE_VERSION.md) ([0.18](../../module0/0C/0.18_TheVersionMatrix.md)). **"Latest" is not a version.**

### Step 3 — ⭐ Draw the thing 1.11 could not show

📄 **NEW FILE** `scripts/PhysicsVision.cs`, attached to your `Marble`:

```csharp
using Godot;

public partial class PhysicsVision : Node
{
    [Export] public bool ShowVelocity { get; set; } = true;
    [Export(PropertyHint.Range, "0.05,2,0.05")] public float Scale { get; set; } = 0.3f;

    private RigidBody3D _body;

    public override void _Ready() => _body = GetParent<RigidBody3D>();

    public override void _PhysicsProcess(double delta)
    {
        if (!ShowVelocity || _body is null) return;

        Vector3 from = _body.GlobalPosition;

        DebugDraw3D.DrawArrow(from, from + _body.LinearVelocity * Scale, Colors.Lime, 0.1f);
        DebugDraw3D.DrawArrow(from, from + _body.AngularVelocity * Scale, Colors.Cyan, 0.1f);
        DebugDraw3D.DrawText(from + Vector3.Up * 0.6f,
                             $"{_body.LinearVelocity.Length():F2} m/s");
    }
}
```

`[UNVERIFIED]` — exact method names and signatures. Check `native_api/cs/` in the addon; the generated C# API is the authority, not this chapter.

Run. **A green arrow points where the marble is going, and its length is how fast.**

### Step 4 — ⭐ Now re-run 1.11's Step 4

### Step 6 — The other kind of addon

Install **Panku Console** *(`Ark2000/PankuConsole`)* — same evaluation, different answer.

It is **pure GDScript**. That means:

| | Debug Draw 3D | Panku Console |
|---|---|---|
| Kind | GDExtension (C++) | GDScript addon |
| Ships | native `.so` per ABI | `.gd` text files |
| APK cost | **MBs** | KBs |
| From C# | **real types, IntelliSense** | 🚨 strings |
| If abandoned | needs the author to rebuild | you can read and patch it |

Enable it and run. Press the console key `[UNVERIFIED]` and you get an in-game prompt — **including on the phone**, which is the point. You can inspect and change live values on the device, where you have no editor and no debugger.

### Step 7 — ⭐ Calling GDScript from C#

Here is the thing nobody warns C# users about.

A GDScript addon defines no C# types. There is **nothing to reference**. You reach it through Godot's dynamic object protocol:

📄 **NEW FILE** `scripts/ConsoleBridge.cs`:

```csharp
using Godot;

public partial class ConsoleBridge : Node
{
    public override void _Ready()
    {
        // The autoload is found by NAME, as a plain GodotObject.
        var console = GetNodeOrNull("/root/Panku");     // [UNVERIFIED] — check the autoload's name
        if (console is null)
        {
            GD.PushWarning("Panku not found — is the plugin enabled and Godot restarted?");
            return;
        }

        // No type. No IntelliSense. No compile-time check. A string.
        console.Call("notify", "Hello from C#");        // [UNVERIFIED] — method name
    }
}
```

**Now misspell it on purpose.** Change `"notify"` to `"notifyy"` and run.

**It builds without complaint.** You get a runtime error, or silence `[UNVERIFIED]`. **The compiler cannot help you, because from C#'s point of view you passed a string to a method that takes strings.**

> 🚨 **This is the real cost of the GDScript ecosystem for a C# user**, and it is exactly what [0.14](../../module0/0B/0.14_LanguageDecisionTable.md)'s decision table needs a row for. Most Godot addons are GDScript. They *work* from C# — Godot's object model is language-neutral — but you consume them **without type safety**, and a rename in the addon becomes a runtime failure in your game.
>
> **The discipline that makes it bearable:** wrap every such addon in **one** C# class, like `ConsoleBridge` above. All the strings live in one file. When the addon changes, you fix one file rather than hunting call sites — and you get a typed API for the rest of your codebase. **Never scatter `Call("...")` through your gameplay code.**

Go back to [0.14](../../module0/0B/0.14_LanguageDecisionTable.md) and add the row: *"consuming a GDScript addon from C# — works, untyped, wrap it."*

### Step 8 — Ship without it

📄 **NEW FILE** `scripts/DebugOnly.cs` — or, better, use a conditional:

```csharp
#if DEBUG
        DebugDraw3D.DrawArrow(from, from + _body.LinearVelocity * Scale, Colors.Lime, 0.1f);
#endif
```

`[UNVERIFIED]` — whether Godot's release export defines `DEBUG`. Check `OS.IsDebugBuild()` as the runtime alternative.

Then verify by exporting a release build and confirming the APK shrank back toward your baseline. **An addon you cannot remove from a release build is a permanent cost, and that changes its evaluation** — record which category each of these two lands in.

Compare the two adoptions. Same checklist, opposite answers on nearly every row — and **neither is the better addon.** Debug Draw 3D gives you a typed API and charges megabytes; Panku gives you an on-device console for kilobytes and charges type safety.

## 🧠 Why it works

### Two ways to extend Godot

| | GDExtension | GDScript addon |
|---|---|---|
| Language | C++, Rust, etc. | GDScript |
| Form | compiled `.so` / `.dll` per platform | `.gd` source |
| Registers | **real engine classes** | scripts and autoloads |
| From C# | genuine types, if the author ships bindings | `Call()` by string |
| Speed | native | interpreted |
| Breaks when | the engine ABI changes | rarely |

A GDExtension registers classes with the engine itself, which is why `DebugDraw3D` appears to C# as an ordinary type. A GDScript addon is *content* — scripts loaded at runtime — so C# meets it through the same dynamic interface it uses for any `GodotObject`.

> 🔬 **Deep dive — why `Call()` works at all.** Every Godot object exposes a name-based method table; that is how signals, `_Ready` and the editor's Inspector all function. Both GDScript and C# sit on top of it, so `Call("notify", x)` is not a hack — **it is the layer the engine actually runs on**. The C# bindings you normally use are a typed veneer generated over that table. Which means: anything reachable from GDScript is reachable from C#, but the typed veneer only exists where someone generated it. That is the whole story of [0.14](../../module0/0B/0.14_LanguageDecisionTable.md)'s ecosystem gap in one sentence.

### Why debug drawing has to be immediate-mode

`DrawArrow` is called **every frame** and draws nothing next frame unless you call it again. That looks wasteful and is the correct design: your visualisation cannot go stale, and you delete one line to remove it — no node to clean up, no lifetime to manage. **The drawing lives with the code that knows the value**, which is why it stays truthful.

## 💥 Break it

1. Call `DebugDraw3D.DrawArrow(...)` from `_Ready` instead of `_PhysicsProcess`.
2. Disable the Debug Draw 3D plugin **without** removing your `DebugDraw3D.` calls. Build.
3. Draw an arrow **per contact point** for 200 rigid bodies at once, and watch your framerate.

## 🔎 Diagnose

**One of these fails at build time, one at run time, one not at all. Which is which — and which is the most dangerous?**

<details>
<summary>Answer</summary>

**1 — Drawing from `_Ready`.** Nothing appears — or a single frame's flicker. Immediate-mode drawing lasts one frame `[UNVERIFIED]`; `_Ready` runs once ([1.3](../1A/1.3_TheSceneTree.md)). **No error, because nothing is wrong**: you asked for one frame of arrow and got it. This is [1.3](../1A/1.3_TheSceneTree.md)'s lesson again — *drawing is a per-frame job, so it goes in a per-frame method.*

**2 — Disabled plugin, calls remain.** 🚨 **This one fails to build**, and that is the good news. A GDExtension registers real types, so `DebugDraw3D` is a compile-time reference; remove the extension and the C# compiler cannot find the type. **Compare with Panku: misspell a `Call(...)` string and it builds fine.** The same mistake is caught by the compiler in one case and not the other, which is the chapter's whole comparison made concrete — and the reason to keep every string in `ConsoleBridge.cs`.

**3 — Thousands of draws per frame.** Framerate collapses. No error; you asked for the work and got it. `[UNVERIFIED]` — where it starts to hurt on your device; **measure it rather than guessing, because the answer on a desktop is not the answer on a phone.**

**The one to be afraid of is #3**, and not because it is the worst symptom. It is the one that **gets committed**. #1 shows nothing, so you fix it immediately. #2 stops the build, so you cannot ship it. #3 works perfectly on your desktop, survives review, and shows up as "the game is slow on my phone" from a player — the class of bug that [5.18](../../../TableOfContents.md)'s optimisation drill exists for.

**Debug visualisation is real work.** It is easy to forget because it feels like it is outside the game, but every arrow is geometry, and the phone does not know you drew it for your own benefit. **Wrap heavy visualisation in a toggle you can find**, and never let a `Draw` call reach a release build unguarded — which is Step 8, and the reason it is a step rather than a footnote.

</details>

**⭐ P2 — Log the evaluations properly.** Both addons, full [0.15](../../module0/0C/0.15_EvaluatingADependency.md) checklist, in [`DecisionsLog.md`](../../../meta/DecisionsLog.md) with today's date and the measured APK deltas. **P3 — Wrap Panku properly.** Extend `ConsoleBridge.cs` into a real typed façade — `Notify(string)`, `Register(string, Callable)` — with every string literal inside it. Then grep your project for `Call("` and confirm the only hits are in that one file.

**🔬 P4 — Predict, then measure, the ABI cost.** Before exporting: look in `addons/debug_draw_3d/libs/`, find the `android.template_release` files for the ABIs you target, and **write down your predicted APK delta**. Then export and compare. Being wrong here is informative — it tells you how much the packager compresses, which is a number you will want again in [11.13](../../../TableOfContents.md).

## ✅ Check yourself

1. What should you do before evaluating any addon at all?
2. What are the two ways to extend Godot, and how does each look from C#?
3. Why is an abandoned GDExtension worse than an abandoned GDScript addon?
4. Why keep every `Call("...")` in one file?
5. Why does debug drawing belong in `_PhysicsProcess` rather than `_Ready`?

<details>
<summary>Answers</summary>

1. **Check whether the engine already does it.** `Debug → Visible Collision Shapes` solves half of this chapter's problem for free. Then write down what the built-in version *cannot* do — that list is your actual requirement, and here it was: arbitrary shapes, vectors, world text, and **anything on the phone**.
2. **GDExtension** — compiled native code registering real engine classes, so C# sees genuine types. **GDScript addon** — scripts loaded at runtime, so C# reaches them through the name-based `Call()` protocol, untyped.
3. Because a GDScript addon is **source you can read and patch**, while a GDExtension is compiled against a specific engine ABI — when Godot changes it you need the author to rebuild, or a C++ toolchain of your own. Acceptable for a debug tool; a poor bet in your shipping path.
4. Because those strings are **unchecked by the compiler**. Concentrated in one façade, an addon's rename is a one-file fix and the rest of your code gets a typed API; scattered through gameplay code, it is a hunt with runtime-only feedback.
5. Because it is **immediate-mode** — each call draws for one frame. `_Ready` runs once, so you get one frame or nothing. Drawing is a per-frame job, so it lives in a per-frame method, next to the code that knows the value.

</details>
